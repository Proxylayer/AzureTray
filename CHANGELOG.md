## [Unreleased]

### Fixed

- **An open submenu never showed a refresh spinner reliably and kept stale rows after a poll finished — the tray menu's in-place refresh only ever reached the root window.** Clicking a "↻ Refresh"-style row inside a submenu started the poll and the plugin duly fired `MenuChanged` at both transitions, but the spinner appeared only sometimes and the submenu's contents stayed pre-refresh until the user moved off the row and re-hovered it. Root cause: `TrayIcon.RefreshOpenMenu` rebuilt the item list and swapped it into `_openMenu` — the ROOT `TrayMenuWindow` only. Submenus and right-click context popups are separate `TrayMenuWindow` instances constructed from a one-time snapshot of the parent item's `Children` (or `SearchProvider("")`), and nothing ever updated them afterwards; since `PluginMenuItem` is an immutable record with no change notification, the wholesale rebuild was the only update mechanism, and it stopped one level down from where the user was looking. The spinner only ran when hover happened to recreate the whole submenu window mid-poll, which is why it looked random. The refresh now cascades: `TrayMenuWindow.RefreshItems` swaps the window's rows (preserving scroll position) and walks the open child chain, re-anchoring each child to its counterpart in the fresh collection and repopulating it in place from the fresh item's `Children`, `ContextItems`, or — for searchable flyouts — by re-running the fresh `SearchProvider` with whatever the user has typed, so the query survives the refresh. A child whose parent row no longer exists is closed along with everything below it. The hover dedup that stops re-hover from tearing down and rebuilding an open submenu compares parent items by reference, so the re-anchor also retargets it at the fresh instance.
  - **Matching a child to its refreshed parent** (`AzureTray.Plugin.Contracts` 1.4.0 → 1.5.0): `PluginMenuItem` gains an optional `Key` init-only property — a stable identity a plugin can set on items whose label changes between rebuilds. Purely additive: no constructor or existing member changed, so plugins compiled against 1.4.0 (PIM 0.10.1, LAPS) load and run unmodified. When `Key` is null the host falls back to Text matching that tolerates a trailing "(n)" count suffix (PIM's "Pending Approvals (3)" style labels), so existing plugins get correct in-place refresh without recompiling; the rule lives in the host's `MenuItemMatcher` (Key equality first and authoritative, then exact Text, then count-stripped Text).
  - **A plugin refresh no longer clobbers the admin menu.** `RefreshOpenMenu` unconditionally rebuilt the *regular* item set, so if a plugin poll completed while the Ctrl+click admin menu was open, the admin menu's contents were silently replaced with the regular menu. The host now remembers which set populated the open menu and rebuilds that one.

- **Approving a management-group-scoped Azure-RBAC request failed with 404 after the popup appeared** (`AzureTray.Plugin.PIM` 0.10.0 → 0.10.1). Follow-up to the fix below: the MG fan-out now correctly *surfaced* the approval, but clicking Approve failed — confirmed in production, three attempts, all `GET …/providers/Microsoft.Management/managementGroups/{mg}/providers/Microsoft.Authorization/roleAssignmentApprovals/{id}` → `404 Not Found`, thrown from `ArmPimClient.ReviewAsync`. Root cause: `ReviewAsync` prefixed the approval's resource scope onto both roleAssignmentApprovals URLs (the approval GET and the stage PATCH), but ARM's Role Assignment Approvals API is a **tenant-level** collection — the documented form (api-version `2021-01-01-preview`) is `GET /providers/Microsoft.Authorization/roleAssignmentApprovals/{approvalId}` and `PATCH …/{approvalId}/stages/{stageId}`, with no scope segment at all; the approval id alone identifies the approval regardless of where the underlying request was made. Subscription-prefixed calls happened to be tolerated by ARM's routing, which is why subscription-scoped reviews worked and the bug stayed hidden; management-group-prefixed calls genuinely 404. Both URLs are now tenant-level — the canonical documented form for every scope — so subscription-scoped reviews are unaffected in behaviour but now also use the correct URL. The unused `scope` parameter was removed from `IArmPimClient.ReviewAsync` end-to-end rather than left dead, and the watcher's "ARM approval has no scope; cannot review" guard went with it: a review no longer needs the scope at all.

- **Management-group-scoped PIM activation requests from other users never raised an approval popup** (`AzureTray.Plugin.PIM` 0.9.1 → 0.10.0). Confirmed in production: another user requested Owner at **Tenant Root Group** (a management-group scope), PIM emailed the signed-in user as the approver, and AzureTray stayed silent. Root cause: the approver feed's ARM fan-out issued `asApprover()` queries **only at subscription scopes** — `PendingApprovalWatcher` built its scope list exclusively from `/subscriptions/{id}` strings, and ARM's `asApprover()` at a subscription never returns requests made at a management group above it. The narrowing set fed to it (`EligibleRolesWatcher.RelevantSubscriptionIds`) had the same blind spot: its scope parser returned null for `/providers/Microsoft.Management/managementGroups/{id}`, so MG-scoped eligibility contributed nothing. The Graph feed only covers Entra directory roles and can never surface an Azure-RBAC request. The result was structural, not transient: no polling interval or refresh would ever have found the request. The fix derives the management-group scopes from the user's own eligibility — `EligibleRolesWatcher` now exposes `RelevantManagementGroupScopes` (persisted in the per-tenant eligibility cache alongside the subscription ids; older cache files load as "none known" and the first poll fills them in), and `PendingApprovalWatcher` fans `asApprover()` out over those MG scopes in addition to the subscription scopes. Deliberately **not** a tenant-wide management-group enumeration: a user can only approve where PIM involves them, eligibility already names those scopes, and the confirmed case (eligible at Tenant Root Group) is covered — a user with no MG-scoped eligibility sends exactly the same requests as before. A request scoped at a management group comes back from both the MG query and every descendant subscription query, so the poll now collapses results on the request's dedup key before they reach the snapshot or the notify loop — one popup, not one per scope that returned it.
  - **A surfaced approval now leaves a trace in the log.** The notify path was silent on success, which made "the popup never appeared" indistinguishable from "the feed never saw the request" during this investigation. Each newly seen pending approval logs one Information line: source (Entra ID / Azure RBAC), approval id, requestor display name and principal id, role, scope, and tenant.

## [0.10.0] — 2026-07-29

### Added

- **Startup is no longer silent in the log.** `Program`, `App` and the paths/version resolution carried zero log statements, so the first thing a log (or the in-app Log Viewer) showed was whatever a hosted service happened to say once it was already running — "the app started but no icon appeared" and "where is my config" both had nothing to read. Startup now narrates itself at Information: version and installed-vs-dev build, the resolved data / plugins / logs / config directories, the configuration that actually changes behaviour (log level and file logging, Azure cloud authority and endpoints, plugin trust mode, the effective automatic-plugin-update choice, the NuGet feed URL, discovery tag and prerelease preference), host build → hosted services starting → started, how many tenants were loaded, a one-line summary of which plugins ended up loaded, the tray icon becoming visible, and "Startup completed in N ms" measured with a `Stopwatch` from the first line of `Main`. Roughly a dozen lines for a normal launch — no per-file or per-registration chatter, no secrets, tokens or user identity, and nothing that duplicates what `UpdateService` and the two polling loops already report.

### Fixed

- **PIM role activation reported "Activation failed" for activations that had actually succeeded** (`AzureTray.Plugin.PIM` 0.9.0 → 0.9.1). ARM Just-in-Time activation issues `PUT …/roleAssignmentScheduleRequests/{guid}` with a client-generated GUID; the `arm` HttpClient's standard resilience handler capped each attempt at 10 s, but ARM's PIM write regularly takes longer, so the socket was aborted at 10 s *after* the server had already committed the request. The resilience handler then retried the identical PUT and ARM answered `409 Conflict` — *"A role assignment request with Id: {guid} already exists"* — which surfaced to the user as a failed activation even though the role had been granted (a production log shows this happening twice). Two fixes: (1) `ArmPimClient` now treats a 409 that names its own request GUID as success, reconciling by re-reading the committed request and returning it, while any other 409 (a different id, a genuine conflict) still throws and a missing reconciled request is still an error; (2) the `arm` and `graph` resilience timeouts were raised — per-attempt 10 s → 30 s, total request 100 s, circuit-breaker sampling 60 s — so the slow path that triggers a retry is far less likely in the first place.

- **The Entra activation-cap policy query was rejected by Graph on every call, and had been since it shipped** (`AzureTray.Plugin.PIM` 0.9.0 → 0.9.1). A production log shows 42 attempts and 0 successes: `policies/roleManagementPolicyAssignments?…&$expand=policy($expand=effectiveRules($select=id,maximumDuration,isExpirationRequired,setting))` returns `400 Bad Request` — *"Parsing OData Select and Expand failed: Could not find a property named 'maximumDuration' on type 'microsoft.graph.unifiedRoleManagementPolicyRule'"*. `effectiveRules` is a collection of the **base** rule type; `maximumDuration`, `isExpirationRequired` and `setting` exist only on the derived types, so naming them in a nested `$select` fails while the query is being parsed, before any data is touched. The clamping feature therefore never read a cap — it fell back to "cap unknown" on every poll, which is exactly what a tenant with no policies looks like, so it read as working. The nested `$select` is gone: `$expand=policy($expand=effectiveRules)` fetches all 17 rules per policy, and correctness beats the payload saving. ARM's policy path was never affected (it reads `properties.effectiveRules` inline off the listing) and is unchanged.
  - **The `scopeType` is now self-diagnosing.** The `$filter` had never actually been evaluated — the request died at `$select` parsing — so `scopeType eq 'Directory'` was unverified, and Microsoft's own v1.0 example for Entra roles uses `'DirectoryRole'`. A wrong value returns an *empty set*, not an error, so it cannot be told apart from a tenant with no policies. The client now queries `'Directory'` first and, if that succeeds with zero assignments, retries once with `'DirectoryRole'`; the value that returns assignments is logged at Information and cached for the session, so the probe costs one extra request once per tenant rather than one per poll.
  - **A zero-assignment read is no longer silent.** A successful-but-empty policy read logs a Warning naming the `scopeType`(s) tried and stating that caps and approval requirements stay unknown; a normal non-empty read keeps its Debug line with the policy and assignment counts.

- **Framework HTTP logging no longer drowns the log.** Of 16,646 Information lines in a 2.5-hour session, ~14,500 came from `System.Net.Http.HttpClient.*` (`LogicalHandler` / `ClientHandler` Start / End / Sending / Received) and Polly's "Execution attempt" telemetry — about five lines per HTTP request across ~2,900 requests, restating what `HostPluginHttpClient` already reports in one line per request (21 lines over the same window). At 3.5 MB per 2.5 hours against a 10 MB cap, the on-disk history held well under a day. Serilog `MinimumLevel.Override` entries now hold the `System.Net.Http` and `Polly` source contexts at Warning, cutting roughly 87% of the volume and making the retained files genuinely retrospective. Nothing else changed: file rolling, retained count, size limit, ring-buffer size, and the app's own `AzureTray.*` / `Plugin.*` levels are all untouched.
  - The two overrides are fixed at `Warning`, so lowering the app's level to Debug or Verbose does not bring the per-handler detail back — `HostPluginHttpClient` already logs each plugin-feed request and response, and the app's own `AzureTray.*` / `Plugin.*` categories still follow the runtime level switch as before. The startup "Logging at minimum level …" line states that the two framework categories are held at Warning.

## [0.9.0] — 2026-07-29

### Added

- **Plugin update detection.** Plugins are published to nuget.org independently of the host, and Velopack ships the host only — so a user on the newest release could be running a months-old plugin with no signal at all. The host now compares what is installed against the feed and surfaces the difference in three places: an **aggregated** toast (one notification listing every plugin with an update — never one per plugin, `NotificationSeverity.Update`, non-auto-dismissing, its action opens Settings), a persistent banner in the Settings → Plugins card, and an **"Update to vX.Y.Z"** button on the plugin's installed row.
  - `PluginUpdatePollingService` (`BackgroundService`) runs the check every `App:Plugins:UpdateCheckIntervalHours` (default `6`, `0` disables), sleeping one full interval first so it never races the Settings window's own check at launch. It dedupes by `packageId → last notified version`, so finding the same update every tick raises one toast, not one per hour.
  - The poll queries the feed with exactly the arguments the Settings browse list uses (empty query, prerelease flag from the shared preference), so it lands on the same entry in `NuGetPluginFeed`'s single cache slot instead of evicting the list the UI is showing.
  - Clicking Update runs the ordinary interactive install pinned to the newer version, so the GHSA advisory prompt, the unsigned-plugin trust prompt, and the required-permissions notification all still fire. Installed plugins remain filtered out of the Available list — the update affordance lives on the installed row, not as a duplicate entry.
- **Installed plugins now record what version they are.** `ExtensionInstaller` writes `plugins/<packageId>/azuretray-plugin.json` (package id, version read from the package's own `.nuspec`, install timestamp, source URL). This is the only version record that survives a DLL which fails to load — the previous source of truth was the live plugin instance, which doesn't exist in that case — and it replaces inferring the package id from the file name. A missing or corrupt manifest degrades to "version unknown": it is logged, never thrown, and falls back to the loaded plugin's version so pre-existing installs keep working until their next update.
- **Opt-in automatic plugin updates** (`App:Plugins:AutoUpdate` seeds it; default **off**, and the user's own choice persists in `%APPDATA%\AzureTray\plugin-updates.json`). When enabled, `PluginAutoUpdater` applies updates unattended — except that it **refuses**, logs the reason, and falls back to the toast for a manual click when: GHSA reports a High/Critical advisory for the new version (or the scan can't run at all); the version on disk is unsigned, so installing the new one would need the unsigned-plugin trust prompt; the plugin uses the legacy top-level `plugins/<id>.dll` layout; or the new package produces nothing loadable. Nothing that would normally ask the user a question is answered on their behalf.
- The user's **prerelease preference is persisted** and shared by the browse list and the update checker, and `App:NuGet:IncludePrereleaseByDefault` — bound but never read since it was introduced — now actually seeds it instead of the view model hard-coding `true`.
- **The requestor's reason is shown to the approver** (`AzureTray.Plugin.PIM` 0.8.0 → 0.9.0). An approve/reject prompt said who wanted which role where, but not *why* — so the one piece of context a decision actually turns on was the one thing missing, and the approver had to open the Azure portal to find it. The prompt now reads `Alice Chen is requesting Global Administrator on Entra ID directory.` followed by a blank line and `Reason: "…"`. It costs no extra request: both providers already returned `justification` on the schedule request (`roleAssignmentScheduleRequests` is queried without `$select`/field narrowing) and both DTOs already bound it — the watcher's projection was simply dropping it. Note this is the *schedule request's* justification (the requestor's words), not the approval step's, which is an approver's own decision comment.
  - The reason goes in the visible `Message`, never only in the collapsed Details expander. It is clamped to 280 characters with an ellipsis, and when clamped the untruncated text is attached as a `Reason` detail row. Whitespace runs (including newlines) collapse to single spaces so the visible copy stays a predictable few lines. New `ApprovalReason`.
  - A missing reason is a real case — the Azure portal and the CLI both accept an empty justification, and ARM documents the field as nullable — so a request without one reads `No reason was given for this request.` rather than a dangling `Reason:`. Requests raised from AzureTray always carry one; its justification prompt is mandatory.
  - Both entry points (the watcher's prompt on a newly-seen approval and clicking the row under Pending Approvals) go through `HandleNewApprovalAsync`, so both show it. The menu row itself is unchanged — it is ellipsized inside the tray popup, where a reason would be unreadable.

### Fixed

- **A long notification message no longer pushes the buttons off the notification.** `NotificationWindow`'s message block wrapped without limit inside a grid of `Auto` rows, so a `Message` long enough to fill the window's 600px cap drove the choice list and the Submit/Cancel buttons past the clip line — the text was readable but the notification could not be acted on, and dismissing it was the only way out. The message and the Details expander now share one height-capped scroll host (`Auto` scrollbars, 280px), while the input and action rows keep their natural height, so the buttons are reachable at any message length. Notifications below the cap are laid out and sized exactly as before — no scrollbar, no height change.

- **Version comparison no longer trusts the order nuget.org returns.** `NuGetPluginEntry.Versions` was built by reversing the search response's `versions` array on the assumption it arrives oldest-first; the NuGet v3 search spec documents no ordering guarantee, and consumers then indexed `Versions[0]` as "newest". Harmless while the only action was "install the latest", wrong for "is a newer version available". Versions are now sorted by parsed SemVer (`NuGet.Versioning`, which has zero package dependencies), and every comparison parses both sides — an unparseable version on either side means "no update available" and is logged, never reported as an update. A prerelease only counts as newer than a release when the user opted into prereleases.
- **Declining an update no longer uninstalls the plugin.** The rollback for a declined install deletes the files it just wrote, which for a per-plugin subfolder means the whole folder — correct for a fresh install, but for an in-place version bump it would have removed a working plugin because the user said "no" to the unsigned prompt. In-place updates (manual and automatic) now snapshot the plugin folder to a temp location first and restore it when the install is declined, throws, or produces nothing loadable.

## [0.8.0] — 2026-07-29

### Added

- **Activation durations clamped to the role's PIM policy maximum** (`AzureTray.Plugin.PIM` 0.6.0 → 0.7.0). The duration prompt offered a fixed `1 hour / 4 hours / 8 hours`; picking a value above a role's policy cap earned a server-side 400 that surfaced as a generic activation failure. The plugin now reads each eligible role's `Expiration_EndUser_Assignment` rule and offers only the standard steps at or below the cap, plus the cap itself when it is not already one of them — a role capped at `PT2H` offers `1 hour`, `2 hours`; one capped at `PT8H` keeps all three. Eligible rows whose cap restricts the choices show it (`Reader  (Dev sub)  ·  max 2h`).
  - Graph: one request per tenant per poll — `policies/roleManagementPolicyAssignments?$filter=scopeId eq '/' and scopeType eq 'Directory'&$expand=policy($expand=effectiveRules($select=id,maximumDuration,isExpirationRequired,setting))` — joined to eligible roles on the assignment's bare-GUID `roleDefinitionId`. `effectiveRules` (not `rules`) so tenant-wide enforced policy is accounted for. No new permission: `RoleManagement.Read.Directory` was already requested.
  - ARM: one request per scope the user actually holds eligibility on (typically a handful, not every subscription), reading `properties.effectiveRules` inline off `roleManagementPolicyAssignments`. The former per-policy `GET {policyId}` round-trip is gone — both the approval rule and the duration rule come out of the listing. Keyed by scope + role definition id, since the same role can carry different policies at different scopes.
  - `IGraphPimClient`/`IArmPimClient`: the never-called `CheckApprovalRequiredAsync` is replaced by `GetRolePoliciesAsync`, which returns approval requirement *and* maximum duration for every role in one lookup. New `RolePolicy` record, `Iso8601Duration` reader (`TimeSpan.Parse` rejects `PT8H`; `XmlConvert.ToTimeSpan` reads it), `ActivationDurationChoices` (choices carry their `TimeSpan`, so a pick is no longer recovered by parsing the display label), and `ArmRolePolicyKey`.
  - `UnifiedEligibleRole` gained `MaxActivationDuration`, persisted in `eligible-roles-{tenant}.json`; older cache files load it as null and the first poll fills it in. A policy read that fails keeps the last known cap rather than downgrading it to unknown.
  - Degrades quietly: reading policies requires the signed-in user to hold a directory role that permits it (Global Reader, Security Reader/Operator/Administrator, Privileged Role Administrator), so a 403 is expected for some users. It is logged as a warning, never blocks activation, and leaves Entra roles clamped to the 8-hour ceiling Microsoft documents for role activation. Azure RBAC has no documented equivalent ceiling, so an unknown ARM cap keeps the previous full list.
- **Remaining time on active PIM roles.** Active role rows in the tray menu now read `Global Administrator  (Directory)  ✓ active · 3h 42m left`. The countdown is the *role assignment's* end time (not the access token's) and is computed when the menu is built — the host rebuilds every item on each tray click, so it is accurate at open and never ticks stale in place. Permanent assignments, and any end time already past, keep the bare `✓ active` marker. New `EligibleRolesWatcher.FormatRemaining`.
- **Post-approval token refresh.** When a PIM activation the signed-in user submitted is approved, the new role's claims exist server-side but the cached access token predates them, so the role used to take effect only when that token rolled over (~60-90 minutes). The PIM plugin now tracks its own pending activations and, on approval, asks the host to force-refresh the tenant's tokens, re-reads the active roles, notifies the user, and rebuilds the menu.
  - `IPluginContext.RefreshTokenAsync(tenantId, ct)` — new default-implemented contract member (returns `false` on hosts that predate it). `PluginApiVersion.Current` 3 → 4, `MinSupported` unchanged at 1; `AzureTray.Plugin.Contracts` 1.3.0 → 1.4.0.
  - Host side: `ICredentialFactory.ForceRefreshAsync(tenantId, scopes, ct)` re-acquires the Graph *and* ARM tokens with a `nbf` claims challenge, which MSAL treats as "bypass the access-token cache" (`CacheRefreshReason.ForceRefreshOrClaims`), so the STS re-issues with the account's current claims. Serialized and debounced per tenant, compares the before/after tokens by hash to report whether a genuinely new token arrived, and never triggers interactive sign-in — `DisableAutomaticAuthentication` stays on and `AuthenticationRequiredException` is logged and reported as `false`.
  - New `PendingActivationWatcher` (60s, matching the approvals watcher) plus a `PendingActivationStore` persisted to `pending-activations-{tenant}.json`, so an approval that lands while the app is closed is still detected. Requests are dropped on terminal refusal (with a warning toast) and after 24h without a decision.

### Fixed

- **ARM roles no longer show `✓ active` because an Entra role shares their name.** Active assignments were fetched from Graph only and reduced to a set of display names, which every Azure RBAC row was then matched against — so an Entra "Owner" activation greyed out an unrelated ARM "Owner" row. `IArmPimClient.ListActiveRoleAssignmentsAsync` now performs a real `roleAssignmentScheduleInstances` read per subscription scope, and matching is per provider on role definition id + scope (an assignment inherited from an ancestor scope still counts), carrying the `endDateTime` the countdown above needs. The eligible-role cache gained an `ActiveAssignments` member; older cache files load as "actives unknown" and are refilled by the first poll.
- **Activation notification no longer claims success when the request went to an approver.** `HandleActivationAsync` discarded the activation response; it now reads the returned status and says "Requested … — awaiting approval" unless the request came back `Provisioned`.
- **Duplicate eligible roles collapsed into one menu row** (`AzureTray.Plugin.PIM` 0.7.0 → 0.8.0). The eligible-role list was a plain union of the Graph and ARM results with no deduplication, so the same role appeared several times: once per grant path when it is reachable through more than one group or access package, and — the dominant source — once per subscription for a management-group-scoped Azure RBAC eligibility, because the ARM fan-out queries every subscription and ARM also returns eligibilities inherited from above the queried scope. A user with one MG-scoped Owner eligibility over 30 subscriptions saw 30 identical rows. New `EligibleRoleDeduplicator` collapses them before the policy caps are attached, so the policy join also runs once per distinct row instead of once per path.
  - Keyed per provider and never across them — an Entra role and an Azure RBAC role can legitimately share a display name, and active-assignment matching relies on the provider split. Azure RBAC rows key on `ArmRolePolicyKey.For(scope, roleDefinitionId)`, the same key `AttachArmCapsAsync` looks policies up with, so collapsed rows are provably governed by one policy; Entra rows key on role definition id + `directoryScopeId`, both case-insensitive.
  - The surviving row is picked deliberately rather than "first wins": a `Direct` eligibility beats a group-derived one (its `linkedRoleEligibilityScheduleId` names the signed-in user, not the group), a usable eligibility id breaks the remaining tie, and the activation cap is the lowest known value across the group — never `null`, which means "unknown" and must not displace a known cap. Applied on the cache-hydrate path too, so a cache file written before this fix does not show duplicates until the next poll.
- **Entra eligibilities scoped to an administrative unit now display and activate at their real scope.** `directoryScopeId` was parsed off the eligibility and then discarded: every Entra row was labelled `Entra ID directory` and every activation and deactivation sent a hardcoded `directoryScopeId = "/"`, so an administrative-unit- or application-scoped eligibility both mislabelled itself and requested a grant at the wrong scope. `UnifiedEligibleRole` now carries `DirectoryScopeId` (and `MemberType`, which drives the dedup tiebreak above); `GraphPimClient` sends the role's actual scope, falling back to `"/"` when absent, so directory-wide roles behave exactly as before. The row label is derived from the scope id alone — an administrative unit's display name is not on the eligibility response and resolving it would cost an extra Graph call per scope, so `/administrativeUnits/{id}` renders as `Administrative unit {id}`.
- **A missing ARM eligibility id no longer kills the row.** `HandleActivationAsync` hard-refused Azure RBAC activation when the eligible row had no eligibility id, leaving it permanently dead in the menu. `linkedRoleEligibilityScheduleId` is optional on ARM's `roleAssignmentScheduleRequests` contract and `ArmPimClient.ActivateRoleAsync` already omits it when blank, so the refusal is now a warning and the activation proceeds.

## [0.2.3] — 2026-05-12

### Added

- **Periodic update check.** A new `UpdatePollingService` (`BackgroundService`) re-runs `IUpdateService.CheckOnStartupAsync` every `App:Update:CheckIntervalHours` (default `1`, set to `0` to disable the loop — startup check still runs). Long-running tray sessions now see new releases without a process restart. `UpdateService` deduplicates by version so the toast doesn't re-pop on every tick.
- **Collapsible Details on notifications.** `NotificationRequest` gained an optional `Details: IReadOnlyList<NotificationDetail>?` init-only property; the new `NotificationDetail(Name, Value)` record is the row type. The notification window renders these inside a collapsed `Expander` beneath `Message` so verbose error context (response body, status code, stack trace, inner exception) stays out of the default toast size. PIM activation failures (`EligibleRolesWatcher.NotifyActivationErrorAsync`) now populate Details from the originating exception and keep `Message` terse — Status (from `HttpRequestException.StatusCode`), Response body (parsed out of `EnsureSuccessOrThrowWithBodyAsync`'s tail), Type, Inner, Stack trace. `AzureTray.Plugin.Contracts` bumped to `0.2.2`.

### Fixed

- **Update feed URL.** Velopack was configured with `SimpleWebSource("…/releases/latest/download")`, which 404s as a directory listing (the alias only resolves when an asset filename is appended). Switched to `GithubSource(repoUrl, accessToken: null, prerelease: false)`, which talks to the GitHub API to discover the latest published release and its `RELEASES`/`.nupkg` assets. `appsettings.json` `App:Update:FeedUrl` is now the bare repo URL `https://github.com/Proxylayer/AzureTray`.

## [0.2.2] — 2026-05-12

### Changed

- **Host permission audit + restructure.** `HostRequiredPermissions` split into two layered sets:
  - `Baseline` — `User.Read` only. What the runtime host actually exercises (sign-in identity, /me lookup, tenant display name resolution).
  - `AdminTools` — `Application.ReadWrite.All` + `DelegatedPermissionGrant.ReadWrite.All`. Only needed by the in-app admin features (Fix Permissions, Create App Registration, App Registration search). A user who never invokes those features doesn't need them functionally.
  - `All` = `Baseline ∪ AdminTools`, used by the aggregation that drives Create App Registration / Fix Permissions provisioning. No behavioural change vs. v0.2.1; the split makes intent legible. Plugins continue to declare their own runtime scopes via `ITrayPlugin.RequiredPermissions`.

### Fixed

- **Log Viewer redesign.** Replaced the `DataGrid` (which truncated "Information" to "Informatio", horizontally scrolled, and made selected rows unreadable) with a virtualized `ListBox` whose rows lead with a 3-char severity glyph (`ERR`/`WRN`/`INF`/`DBG`/`VRB`/`FTL`) and an accent-colored stripe. Messages wrap. Exception text renders inline under the message in muted monospace. Class label is right-aligned and click-to-filter. Dropped the date pickers (not useful for a 500-entry ring) and collapsed the two filter rows to one. New `LevelToGlyphConverter` + `NullToVisibilityConverter`.
- **Host crash on shutdown.** `TrayIcon.Dispose()` called `_services.GetService<IPluginLoader>()` to unsubscribe `PluginsChanged`, but the IServiceProvider is disposed *before* singleton `Dispose()` runs. Cached the loader at `Start()` time and use that reference in `Dispose()` — no more `ObjectDisposedException` at exit (the `[FTL] Host terminated unexpectedly` entries).
- **PIM activation 400 Bad Request.** Both `GraphPimClient.ActivateRoleAsync` and `ArmPimClient.ActivateRoleAsync` were sending `startDateTime = DateTimeOffset.UtcNow.ToString("o")`. By the time the request reached the server, that timestamp was a few hundred milliseconds in the past, and Graph/ARM 400 any schedule with a past start. Now passes `null` (omitted via `WhenWritingNull`) so the service computes the instant itself. Matches legacy `Azure.PIM.Tray` behaviour.
- **Graph error response bodies now visible.** `AppRegistrationGraphClient` previously used `EnsureSuccessStatusCode` which discarded the response body, leaving Fix Permissions / Create App Registration failures as opaque "403 Forbidden". Now uses `EnsureSuccessOrThrowWithBodyAsync` (same pattern already in the PIM clients) so the user sees `Authorization_RequestDenied: Insufficient privileges...` and similar Graph error codes in the log.
